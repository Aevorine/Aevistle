# Aevistle 0.3.28

一句话：**邮件一直都收到了。是"要不要提醒你"这一步，把 100% 的新邮件都吃掉了。**

从 0.3.24 到 0.3.27，一共四个版本在修「收不到新邮件提醒」，每一次都说修好了，
每一次用户回来说还是没有。这一版不是第五次猜——是先把证据拿到手，再动代码。

---

## 一、先看证据

在报告问题的这台电脑上，直接读应用自己的数据和 Windows 的通知记录：

| 量到的东西 | 数字 |
| --- | --- |
| 配置的收件账户 | 5 个（4 个 Gmail + 1 个 QQ） |
| 缓存的邮件 | 187 封 |
| 同步错误 | **0** |
| 最近一次同步距现在 | **12 秒** |
| **其中未读的** | **0 封**（187 封全部是已读） |
| Windows 记录的 Aevistle 通知总数 | 40 条 |
| 最后一条通知的时间 | **2026-08-19 17:47** |

然后把两边对起来看——在最后一条通知之后到达、但没有引起任何通知的邮件：

```
08-20 18:16  账户 A     seen=True  uid=305  （主题略）
08-20 09:55  账户 B     seen=True  uid=45   （主题略）
08-19 18:03  账户 B     seen=True  uid=43   （主题略）
```

三封邮件，全部收到了，全部进了列表，**全部是 `seen=True`**，一条通知都没有。

「未读 0 封」不是应用算错了。用邮件服务商自己的接口独立查了一遍，
`is:unread in:inbox` 返回**空**——服务器那边确实一封未读都没有。

## 二、于是就清楚了

`newArrivals` 判断"要不要提醒"有三条规则，第二条是：

> **别的设备已经读过的，不算新邮件。**

这条规则本身没错——手机上两分钟前刚看过的邮件，电脑再响一次是打扰。

**但它有个前提：你的信箱里"未读"这个状态是有意义的。**

如果手机上还有第二个邮件应用在收同一个信箱（系统自带邮箱、Gmail App、
QQ 邮箱 App 都算），那封邮件往往在**到达后几秒内**就被标成已读。
等 Aevistle 看过去的时候，**没有任何一封是未读的**。

于是这条规则不是"偶尔拦下一封"，而是**永远拦下每一封**：

- 邮件正常收到 ✔
- 列表正常显示 ✔
- 规则判定：已读，不提醒 ✔
- **结果：这个功能在数学上不可能触发**

而且它三个平台一起失效，因为三个平台用的是同一条规则。

### 前四个版本为什么没找到

因为**这个决定从来没有留下过任何记录**。

判断函数算完就把答案扔了。所以想验证一个修复，唯一的办法是等真邮件来、
盯着屏幕角落看。什么都没发生的时候，六种可能的原因**长得一模一样**：

没有新邮件 / 设置关着 / 在免打扰时段 / 首次同步只建基线 / 邮件太旧 / 别的设备已读。

分不出来，就只能挑一个改，改完再等。四个版本就是这么过去的。

## 三、改了什么

### 1. 决定过程留下记录

现在每次同步都算出一份完整的账，并且**账目必须平**：
这次同步拿回来 N 封，其中新的 M 封，M 封里提醒了几封、被哪条规则拦下几封——
加起来必须正好等于 M。**一封邮件不允许"消失"在任何一条规则的缝里。**

有东西可说的时候才写一行到「记录」页新增的**「收件」**分类里：

```
收件诊断 · 账户 A
2 封别的设备已经读过，按规则没有提醒
```

```
收件诊断 · 账户 B
提醒了 1 封
```

没有新邮件的同步**一个字都不写**——1 分钟同步间隔 × 5 个账户 = 一天 7200 行，
那会把这个日志本来要记的发信记录整个挤出保留期。

**只记数字，不记发件人、主题、摘要。**这份日志能导出成 CSV，
收件诊断不能让那个导出变成信箱副本。

### 2. 新开关：「别的设备读过的也提醒我」

设置 → 通知，就在「收到新邮件时通知我」下面。

**默认关**，因为那条规则对"未读有意义"的信箱是对的，不该替所有人改掉。
但它只关掉第二条规则，其他三条一条不动：

- 首次同步仍然只建立基线，不会一口气念完整个信箱
- 一周前的邮件仍然不算"刚到"
- 已经见过的邮件仍然不会再提醒一次

### 3. 手机上那三个开关，以前是装饰

查代码的时候发现的，跟上面是同一类问题：

| 开关 | 电脑 | 手机（应用关着时的后台通知） |
| --- | --- | --- |
| 收到新邮件时通知我 | 生效 | **完全没读** |
| 免打扰时段 | 生效 | **完全没读** |
| 别的设备读过的也提醒我 | 新增，生效 | 新增，生效 |

前两个的后果很具体：**把「收到新邮件时通知我」关掉，应用开着的时候安静了，
关掉之后照样弹**——而后者恰恰是这个开关真正管的那种通知。

现在三个都读了。免打扰时段的判断是照着电脑端一行行对过来的，
包括它**失败的方向**：时间格式读不出来时判定为"不在免打扰"。
因为一个时间字符串没解析成功就把邮件压下去，是比半夜响一声更糟的结果。

### 4. 同步不再用可写方式打开信箱

`electron/imap.ts` 里所有读取路径都带 `readOnly`，只有主同步那一行漏了——
它用 `SELECT` 而不是 `EXAMINE` 打开 INBOX。

**目前没有造成后果**：取正文用的是 `BODY.PEEK[]`，不会标已读。
但"只要没人再加一个不带 PEEK 的取信就没事"不是值得依赖的性质，
而它出事的样子是最糟的那种——**一个只该看看的应用，把你所有设备上的邮件都标成了已读。**

改成 `readOnly`，并且新门禁盯着：`getMailboxLock(INBOX_PATH)` 不带参数的写法，
以后一出现就红。

## 门禁

新增 `check:inbox-delivery`，**40 条**，真的跑代码：

| 组 | 钉死什么 |
| --- | --- |
| 账目要平 | 每封邮件恰好落进一个桶；两条规则都能拦的邮件只算一次；未建基线的同步也要如实报告看到了多少 |
| 开关要窄 | 打开它，一封已读的新邮件会被提醒；**同时**它不能让首次同步开口、不能放宽时间窗、不能让已见过的邮件再响 |
| 老规则没变形 | `newArrivals` 的行为逐条对齐，`check-new-mail.mjs` 量的还是同一个东西 |
| 信箱是只读的 | INBOX 必须 `readOnly` 打开；正文必须 `BODY.PEEK[]` |
| 记录真的写了 | 报告必须在两道门之前算出来（否则永远说不出是哪道门拦的）；没事的同步必须一个字不写；日志里不许出现主题和发件人 |
| 手机一致 | 三个开关都要读；两个平台默认值必须一样；缺失的设置回落到应用默认而不是 false；时间读不出来要往"不静音"的方向失败 |

`--selftest` 把「别的设备已读」这条规则改回原样（也就是报告问题时的状态），
门禁立刻红在那一条上——证明它量的确实是这个 bug，不是别的。

---

## 装完之后

装 0.3.28，然后按你的情况选：

**如果你手机上还有别的邮件应用在收同一个信箱**（大概率是这种）
→ 设置 → 通知 → 打开**「别的设备读过的也提醒我」**。

**不确定的话**，先什么都不改，等下一封邮件到，然后去 **记录 → 收件**。
那一行会直接告诉你这封邮件为什么没响。
