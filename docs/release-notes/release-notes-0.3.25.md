# Aevistle 0.3.25

一件事：**你不在的时候来的邮件，现在会告诉你了。**

这一版从一个报告开始 ——「手机、电脑、平板都收不到邮件通知」。查下来不是一个毛病，
是五个，它们各自都能独立造成同一个结果：**邮件到了，没人吭声。**

后四个是在验证第一个修复的过程中挖出来的。

---

## 一、程序没开的那段时间，邮件被吞掉了

这是最主要的一个，也是最难看出来的一个 —— 因为它不报错，什么日志都没有。

判断"这封信要不要通知"有三条规则，其中两条共用了一个假设：**上次看这个邮箱是不久以前，
而且是这个进程自己看的。** 应用一关，两条都不成立了：

| 规则 | 本意 | 关机后变成了什么 |
| --- | --- | --- |
| 启动后第一次同步只"建立基线"，不报 | 防止一开应用就把整个收件箱念一遍 | 关机期间的信全被当成"基线"，一条不报 |
| 只认 30 分钟以内的信 | 防止离线一周后回来念一整周的旧信 | 早上开机，昨晚的信已经八小时前了，超窗 |

两条叠起来：**晚上关电脑，半夜来信，早上打开 —— 什么都不会说。**

改法不是把窗口调大（那样离线一周回来就要刷屏），而是换掉那个坏掉的假设：

- **基线从硬盘上恢复。** 上次退出前存下来的邮件列表，就是"我上次知道有哪些信"，
  它一直在硬盘上，只是没人拿来用。
- **时效窗口跟着"你上次看过的时刻"走。** 上次同步是八小时前，那八小时内的都算新的；
  上次同步是一分钟前，那还是按 30 分钟算（永远不会比原来更窄）。上限七天 —— 关机一个月
  回来，不会给你念一个月。

第三条规则原封不动：**在别的设备上读过的信，这里永远不响。**

安卓端同样改了，而且那边更要紧：手机被省电管家冻上几小时是常态，醒来时那些信必然
超过 30 分钟。

## 二、真正"退出"之后，一条都收不到 —— 这是结构决定的

桌面端所有通知都由**窗口**发出。后台那条 IMAP 长连接虽然跑在主进程，但它收到新邮件只做
一件事：把消息转给窗口。**窗口不在，就没人发通知。**

实测过三种状态：

| 状态 | 结果 |
| --- | --- |
| 窗口开着 / 最小化 | 通 |
| 关闭窗口，缩到托盘（窗口真隐藏，进程还在） | 通 |
| 托盘里点"退出"（进程没了） | **一条都没有，而且不可能有** |

第三种不是 bug，是"没有进程就没有代码在跑"。要解决只能让别的东西把它拉起来。

新增一个开关：**设置 → 系统 → 「退出之后也继续收信」**（默认关）。打开后会注册一个
计划任务，每 15 分钟以**你自己的账户身份**（不提权、不是 SYSTEM）静默启动一次应用；
应用已经在跑的时候什么也不做。设置里直接写着删除它的命令，随时可以撤销。

同时改掉了一个会让这个功能变成灾难的地方：**第二个实例原本会把窗口弹到最前**。带上这个
计划任务，那就是每 15 分钟被打断一次，比原来那个"收不到通知"还糟。现在带 `--hidden`
启动的那一次不再抢屏幕，而你自己双击图标启动的仍然会正常打开窗口。

## 三、一个能用但慢的账号，被当成了"连不上"

有个账号从三天前起就没同步成功过，错误写着 `TimeoutError: No answer from the server
within 10 seconds` —— 读起来就是"这个邮箱连不上"。

它连得上。同一份凭据、同一台机器，给足时间去连：

```
慢的那个账号     登录耗时 36.7 秒
另外四个账号     登录耗时  1 - 5 秒     （同一个服务商，同一个端口）
```

而每次连接的预算是 **10 秒**。于是每次都超时，每次都失败，永远收不到那个账号的信。

现在：**你配置的那个端口超时之后，再耐心重试一次（最长 90 秒）。** 只有已经失败的账号
才付这个代价，健康的邮箱一点都不会变慢。

这里有个坑值得记下来：第一版判断条件写的是"最后一个错误是超时",看起来完全正确，
**但永远不会成立** —— 端口阶梯有三级，第一级（你配的 993）才是会卡住的那个，
第二三级是备用端口，真实服务商会在几毫秒内拒绝。所以循环结束时"最后一个错误"是
"连接被拒绝"，不是超时。改成盯"你配置的那一级是不是超时了"。

## 四、越重试越慢 —— 同步把自己掐死了

修好上一条之后，那个账号还是不行，而错误从 `within 10 seconds` 变成了
`within 90 seconds` —— 更耐心了，却更连不上了。

原因：那个邮箱同步一轮要 **152 秒**，而同步间隔设的是 **1 分钟**。上一轮还没结束下一轮
又开，对同一个邮箱堆起越来越多的并发连接。而一个本来就慢的服务商，面对一堆同时打来的
连接只会更慢。**应用自己的重试，就是让它一直失败的原因。**

现在：**同一个账号正在同步时，不再开第二个。** 释放写在 `finally` 里 —— 只在成功时释放
的话，一次失败就会让这个账号永远被标记成"正在同步"，那是同一个故障换了张脸，而且更难发现。

## 五、失败的同步，会把已经收到的邮件抹掉

这一条最严重，因为它是**数据丢失**，而且症状看起来完全不像是错误处理的问题。

实测记录：

```
17:43:03   同步成功    缓存邮件 29 封 → 42 封    错误清空
17:45:32   倒退回去    缓存邮件 42 封 → 29 封    lastSyncAt 退回三天前，旧错误复活
```

没有任何邮件被删除。是一个**开始得更早**的同步终于失败了，而它的失败分支把自己开始时
持有的那份账号快照，整个盖到了新结果上。

那份快照天然是陈旧的：同步定时器持有的是同一个闭包，跨很多次触发不更新，所以快照可能是
好几分钟、好几次成功同步之前的。写回去不是"稍微旧一点"，是**把已经抓回来的邮件扔掉**。

现在：**一次失败只知道一个新事实 —— 它失败了。所以它只准写这一个字段。**

这也解释了为什么那个账号"三天里从来没好过"：哪怕它偶尔成功一次，也会被随后的失败抹平。

## 安卓：多了一行能回答"为什么全绿还是收不到"的状态

设置里原本有三行权限：通知、精确闹钟、电池优化。**这三行可以全部显示"已允许"，而邮件
一封都收不到** —— 因为厂商自己的「自启动管理」不是 Android 权限，没有 API，从应用内部
根本看不见，它会把后台同步服务直接杀掉。

新增第四行：**「后台收信服务」运行中 / 已被停止 / 不需要**。这是唯一一行不是权限的状态，
它直接去看服务此刻还在不在。显示"已被停止"时旁边出现「允许自启动」按钮，直接跳到
华为、荣耀、小米、OPPO、vivo、三星各自的管理页；跳不过去就退回应用详情页 —— 不留死按钮。

## 门禁

`check:new-mail` 这道门禁**从 0.3.24 起就一直是红的，而那个版本还是发出去了。**

0.3.24 把安卓那边的规则从 `InboxSyncWorker.java` 搬到了 `InboxSyncRunner.java`，
而门禁还在读那个已经被搬空的旧文件。它的正则匹配不到任何东西，于是"两边实现必须一致"
这项检查**静默地停止了比较** —— 26 项里 5 项直接失败，`npm run check` 整条链是红的。

一道指着空文件的门禁，比没有门禁更糟：它会报一个自己已经看不见的问题。

这一版修好了它（26 → 53 项），并新增四道：

| 门禁 | 钉死什么 |
| --- | --- |
| `check:slow-imap` | 慢服务器不等于坏服务器；重试只准一次，不准每级都来一遍 |
| `check:background-mail` | `--hidden` 拉起绝不抢屏；开发版绝不写计划任务；关掉必须删干净 |
| `check:keepalive` | 服务状态不准从权限推导；自启动按钮不准掉进 `else` 跑去开电池对话框 |
| `check:sync-overlap` | 同账号不重叠；失败也要释放锁 |
| `check:sync-rollback` | 一次失败只准写"错误"这一个字段 |

每一道都验证过：**故意把它要测的东西弄坏，它会红。**
