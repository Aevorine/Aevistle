# Aevistle 0.3.0

手机端的一次结构性改版：主页从一串一模一样的行，换成一块有**固定容量**的宫格；
宋体与 Times New Roman 回来了；三处实测出来的卡顿点修掉了。

还有一件不太好看但必须说的事：**上一轮用来保证「界面统一」的那个检查脚本，其实
一直没有真的在检查。** 详见最后一节。

---

## 主页：一串行 → 一块宫格

以前手机主页是 11 行长得一样的条目：五个只能从这里进的页面，加六个从设置里提上来的
功能。**11 行同一种形状，说不出哪一个更重要**；而且每加一个功能就多一行——这正是
「以后新加的功能会不会把界面搞乱」这个担心的来源。

一串列表没有容量上限，所以它没法给出承诺。宫格可以。

现在是：一块强调色头图 + 三个数字（待发 / 已发 / 错误）+ **八格宫格**。
其中七格按这台设备**实际打开过的次数**排序，第八格永远是「更多」。

关键在那个「八」：**这一屏的高度和排布，不再取决于总共有多少个功能。**
以后加到第十二个、第四十个，改变的只是哪七个排在前面，界面本身不动。
这就是「未来新置功能不会影响界面美感」——写成一个上限，而不是写成一句愿望。

**排序不会在你手底下动。** 顺序在应用启动时定好，整个使用过程中不变——
今天点的次数，排的是明天的宫格。否则你点第三格，它立刻跳到第一位，
等你关掉窗口回来时东西已经换地方了，那样反而记不住。
打平时也是稳定的（新装的机器按预设顺序，不会莫名其妙自己重排）。

使用次数只存在本机，**不参与设备间同步**——手机和电脑的用法本来就不一样，
一份排序只有描述你手上这台设备时才有用。

电脑端不变：它有九个侧边栏标签和足够的宽度，既没有这个问题，也没有 360px 的约束。

## 宋体 与 Times New Roman

0.2.0 把全应用改成了黑体。这一版改回来：**中文宋体，英文、数字与标点 Times New Roman**，
按字符自动分派（同一句话里「Aevistle 定时发送」的两半各走各的字体）。

字号仍然是那一套刻度，用途绑死：

| | | 用在哪 |
|---|---|---|
| 小四 | 16px | 正文、输入框、按钮、任何当句子读的东西 |
| 四号 | 18.67px | 功能名、区块名 |
| 小二 | 24px | 屏幕标题 |
| 五号 | 14px | **只给数据**：时间戳、计数、标签 |

**为什么 14px 那一档不会难看：** 宋体是给纸设计的，横笔画比竖笔画细得多；手机屏上
一个 14px 的宋体横笔画占不到一个物理像素，只能被丢掉或抹成灰——这是小字宋体在屏幕上
发虚的物理原因。而 14px 这一档按规则**只放数据**，也就是数字和英文，它们本来就走
Times New Roman，笔画均匀，不吃这个亏。中文从 16px 起步。

**代价说在明处：** 安卓上没有任何宋体，所以随包内置了一份 4.25 MB 的思源宋体做兜底，
APK 因此从 5.2 MB 涨到约 9.5 MB。Windows 和 macOS 上系统自带真正的宋体与
Times New Roman，**一个字节都不会下载**——字体声明里系统字体排在内置文件前面。

顺带把行距从 1.6 调回 1.65。当初调低是因为「黑体笔画均匀，行与行自己分得开」；
换回宋体后这个前提没了——宋体要靠行间的空隙，才不至于让上一行的细横笔画看起来
黏在下一行上。代价是每屏少约一行内容。这笔交易的方向是对的：你要的是眼睛舒服，
不是多看见一行。

## 跑得更快的三处（都是实测出来的位置，不是泛泛的优化）

**一、时间显示不再反复重建格式化器。**
`src/i18n/index.ts` 里每显示一个时间就新建一个格式化器，全应用 55 处调用，
列表里**每一行都要新建一次**——而新建格式化器是 JS 引擎里最贵的操作之一。
现在按「语言 + 时区 + 所有选项」缓存。实测：2 万次时间格式化 + 5 千次体积格式化，
在缓存热了以后**新建 0 个**格式化器（改之前是 2.5 万个）。

正确性用了 608 项断言逐条对拍（六种语言 × 四个时区 × 18 组选项），
并且故意做了两份「写坏的」版本做反向对照，确认测试本身不是摆设——
其中一份漏掉时区的版本立刻暴露出「日期差一天」的静默错误。

**二、吸顶栏不再开毛玻璃。**
页面标题栏和底部操作栏原来是「吸顶 + 模糊」，这是安卓 WebView 滚动最贵的一种写法：
每一帧都要把整屏读回来重算。现在换成不透明实色，肉眼几乎看不出差别。
全项目现在只剩一处 `backdrop-filter`，值是 `none`。

**三、工作日历的假日标签不再一次全画出来。**
导入多年假日预设后，那一屏会一次渲染上千个标签，而且每个标签内部还要新建一次
时间格式化器。现在一次显示 60 个，其余按需展开。

## 关于「界面统一」——这一节请一定读

0.2.1 的发布说明里写着：*「实测最大档下，手机上可点控件仍然只有两种高度」*。

**那句话是错的，因为写出它的那个检查脚本没有真的在检查。**

`check-tap-targets.mjs` 存在的目的，是走一遍真实页面、量出每个控件的实际尺寸，
用数字来保证界面统一（前四轮「界面统一」都是靠眼睛看，每一轮都散掉了）。
这一版发现它有三个问题：

1. **它连不上应用。** 它去连 `127.0.0.1:5199`，而开发服务器实际在 `5273`。
   而且它自己的注释写着「npm run check:tap 会帮你起服务器」——并没有。
2. **它没被算进发布前的检查链里。** 所以就算它红了也拦不住任何东西。
3. **它只量了一屏。** 它加载应用后量的是落地的那一屏（撰写页），
   那一屏只有 **1 个**字段标签、**1 个**输入框、**0 个**卡片标题——
   「同一种文字只能有一个字号」这条规则，**4 项里有 3 项永远不可能失败**。
   主页、收件箱、设置页从来没有被加载过。

现在它自己起服务器、自己关掉，走遍**全部 33 个屏幕 × 5 种设备尺寸**，
并且每屏打印控件数量，一个空屏再也不可能悄悄通过。它已经进了发布前的检查链，
整轮约 50 秒。

### 顺便发现：那条「一屏最多 4 种控件高度」的规则本身是错的

修好之后它第一次报出电脑端有 **11 种控件高度**，看着像大问题。查下去发现不是：
那是 **17 种不同类别的控件**（按钮、图标钮、标签片、分段控件、色卡、日历格……），
**每一类内部都是统一的**。这条规则量的其实是「这一屏有几种控件」，那不是缺陷指标。

而且它在「字体最大」档下必然误报：控件的最小高度是固定像素、不随字号缩放，
但控件里的**内容**会长——一块放着 20px 数字的卡片，数字变 25px 时它当然会变高。
全局计数分不出「这是设计如此」和「这是走样了」。

所以换成了一条更严的规则：**同一类控件，在同一个尺寸下只能有一个高度**
（容差 2px，因为分数像素四舍五入）。这条能抓到全局计数抓不到的问题——
同一类控件内部裂成两个值，在旧规则下只算「1 种高度」照样放行。

换完之后，它抓出了两处真问题，**都是「同一种文字两个字号」**：

1. **撰写页的字段标签是四号(18.67px)，全应用其他地方是小四(16px)。**
   这条只在撰写页生效的规则，和字号阶梯自己的定义冲突——阶梯里写着
   「小四 = 正文、**标签**、按钮、输入框」。已删除，字段标签全应用统一为小四。
   省下来的高度全部进了正文框，因为它是那张卡上唯一会自己撑开的元素。
   改完实测（360×800 手机，首屏）：**正文框 328×570，占撰写页高度的 87.2%**，
   标签行 28px，横向溢出 0px，七个格式按钮全部可见无需滚动。
2. **设置页的 PIN 码输入框是 14px。** 这不只是不统一——**低于 16px 的输入框会让
   手机在你点进去时自动放大整个页面**，而这偏偏是要你输六位数字的那一屏。
   `.mono` 这个类本来是给 SSL 报错、文件路径这类「只读的机器文本」用的，14px 合理；
   落到输入框上就不合理了。现在按元素是不是输入框来区分。

修完再跑：**五种设备尺寸、33 个屏幕，零违规。**

**范围说明：** 这一轮做的是手机和平板。电脑端经过上面两处修复后也是干净的，
但电脑端的其他改进（比如设置页 82 个控件的信息密度）不在这一轮里。
