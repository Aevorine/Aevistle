# Aevistle 0.3.6

这一版是 12 件点名的事。其中**两件报上来像是"功能不够"的，查下去是同一类 bug**：
东西一直都在，只是存到硬盘上的时候丢了一半，再读出来就对不上号了。

收件人名单是这样丢的，打不开的图片也是这样丢的。

---

## 一封信还发给了谁 —— 服务器早就告诉我们了

**报告的是**：想知道发件人把这封信发给了哪些人，QQ 邮箱能显示。

服务器**一直**把完整的收件人名单发过来了。取信时请求的是 `ENVELOPE`，那里面本来就
含 To、Cc、Bcc、Reply-To 四组地址。丢在了往本地存的那一步：

```ts
to: formatAddress(row.envelope?.to?.[0]),     // 只取了第 [0] 个
```

`formatAddress` 的签名只接受**一个**地址对象 —— 从函数签名开始就装不下一个名单。
`cc` 一个字都没写过。安卓侧是另一套独立实现，同样只要了 `RecipientType.TO`。

现在两端都存下完整的 `toAll` 和 `cc`。展开一封信的详情，收件人和抄送各占一行；
超过 3 个人时先显示前 3 个、后面标"还有 N 人"，点一下展开全部；旁边一个
"复制全部收件人"，一按就把所有地址逗号分隔放进剪贴板，可以直接粘到写信框里。

### 关于密送，说一句实话

**密送（Bcc）看不到，不是这个软件做不到。** 邮件在投递时，发送方的服务器就把
Bcc 那一行**删掉了**才发给各个收件人 —— 那些字节根本没到你的邮箱。QQ 邮箱同样
看不到，它显示的是"收件人 + 抄送"。

所以详情区最后有一行小字把这件事说清楚，而不是留一个空的"密送"栏让人以为是 bug。

## 打开邮件，5 张图片加载不出来

**这不是隐私设置挡的，是一个真 bug**，而且桌面和安卓各有一个，成因不同。

邮件里的图片分两种，这一版把它们彻底分开对待：

| | 内嵌图片（`cid:`） | 远程图片（`http://…`） |
|---|---|---|
| 字节在哪 | **随邮件一起下载，已经在你硬盘上** | 在发件人的服务器上 |
| 显示它要不要联网 | **不要** | 要 |
| 会不会泄露你的 IP | **不会** | 会 |
| 这一版怎么处理 | **修好 bug，直接显示** | 默认不下载，见下一节 |

用户看到打不开的那 5 张，是**内嵌图**。

### 桌面：缓存里没有存放"图片编号"的位置

正文缓存的数据结构 `CachedBody` 只有 `text` / `sanitizedHtml` / `remoteImages` /
`icsParts` 四个字段 —— **没有一个位置能放附件信息**。首次解析时明明算出了带
`cid`、`inline`、真实类型的完整附件对象，但只有文件字节落了盘，这些信息全丢。

重新打开时走的是"扫一遍附件目录、按文件名猜类型"重建，产出的对象没有 `cid`、
`inline` 恒为 `false`、类型靠后缀猜。而渲染侧要靠 `cid` 把图片和正文里的占位符对上号，
对不上就**直接把图片地址删掉** —— 不报错、不显示破图框，图就这么消失了。

更糟的是同步时会提前把正文写进缓存，所以**用户第一次点开这封信，走的就已经是丢了
编号的那条路**。

现在缓存里存了这份"文件名 → 编号/类型"的对照表。往返验证：改之前读回来是
`cid=undefined, inline=false, mime=application/octet-stream`，改之后是
`cid=hero@example, inline=true, mime=image/jpeg`，全部通过渲染侧的守卫。旧缓存
（没有这个字段的）仍然能正常打开，退回原来的行为，不会崩。

**顺手修的另一个 bug**：两个同名附件（两张都叫 `image.png`）以前会**互相覆盖**，
后一张把前一张的内容盖掉。现在第二个存成 `image (2).png`，两个文件各读各的。

### 桌面：类型判断也在猜

内嵌图常常**没有文件名**，会被兜底命名成 `attachment-0` 这种没有后缀的名字。读取时
按后缀猜类型，猜成 `application/octet-stream`，不在可预览白名单里，于是返回空 ——
图片又一次静默消失。而真实类型在第一次解析时**本来是知道的**，只是没存。现在优先用
存下来的真实类型，拿不到才回退去猜。安全校验（路径必须在附件目录内、必须过白名单）
一条没放宽。

### 安卓：`cid` 压根没写过

安卓侧的附件处理**完全没有写 `cid` 这一项**，而且硬写了 `path: ""`、`inline: false`。
渲染侧的守卫是 `if (!a.cid || !a.path) continue` —— 两个条件同时不满足，
**安卓端内嵌图片 100% 一张都显示不出来**。

现在写出真实的 `cid`（和桌面用的是**同一个**规范化函数，不是各写一份）、真实的
`inline`、真实的落盘路径，并且把没有文件名的内嵌图也存下来（以前会被跳过）。
判定规则从三处各自复制的表达式合并成一个函数 —— 那三处以前决定的是同一个下标，
错一位就是下载到别人的文件。

## 防追踪：远程图片默认不再自动下载

**为什么这是隐私问题**：邮件里的远程图片，是一个指向发件人服务器的网址。你打开邮件的
那一刻，程序去取那个文件，对方就同时知道了三件事 —— **这个邮箱是活的**、
**你什么时候读的**、**你家宽带的公网 IP**。营销邮件里那张 1×1 的透明图，存在的唯一
目的就是这个。

这个版本之前，默认是**自动下载**。

现在默认改成**不下载**，和 Thunderbird、Apple Mail 一样：

- 邮件顶部一条浅蓝色（不再是黄色警告）的提示，写清楚"这封信里有 N 张图片放在对方
  服务器上，还没下载"，右边第一个就是显眼的**"加载 N 张图片"**按钮，按一下就出来；
- 旁边第二个按钮**"始终允许 example.com"**，按了之后这个发件人以后的信自动显示，
  不再问；
- 这封信如果**有内嵌图**，提示会多一句"随邮件一起下载的图片不受影响，已经显示了"，
  免得以为那些也被拦了；
- 加载失败不再只说"有 N 张没能加载出来"，会说清是**这个版本不支持取图**（这种情况
  不给重试按钮，因为重试必然一样失败）、**你现在没联网**、**对方服务器没给**，
  还是**出错了**（出错会把原始报错原样贴出来）。

### 多加了一道网络层兜底

在这之前，网页界面发不出对外请求全靠三件事：净化时改写图片地址、页面的内容安全策略、
以及正文框里不许跑脚本。**没有网络层的兜底** —— 全项目搜不到任何请求拦截钩子。

现在加了一道：界面进程发往非本机地址的请求**一律拦截并记一行日志**。同时收紧了权限
申请 —— 摄像头只在扫配对码（视频、不含麦克风）时放行，麦克风、定位、通知、MIDI、
HID、串口、USB、屏幕录制、剪贴板读取**全部拒绝**并记日志。

### 已读回执：查过了，本来就是安全的

代码里只有"你发信时可以主动要求对方回执"这一个方向。**没有任何代码会替你回复别人的
回执请求** —— 别人发信要求回执，你这边不会告诉他"我读了"。这条不用改。

## 读过的邮件，过一会又变回未读

**这个 bug 的成因和上面两个是同一类：本地知道的事，被一次同步覆盖掉了。**

标记已读是**先改本地、再推服务器**：界面立刻变成已读，`\Seen` 标志随后通过网络发出去。
而同步很频繁 —— 每 5 分钟一次、邮件服务器每次推送通知一次、**每次切回应用还要再一次**。

同步结果回来时，整条消息列表被**整个替换**成服务器说的样子。这个地方原本已经为两类
数据写了"向前结转"的保护（删除记录、图片偏好），注释里写得清清楚楚"同步结果只对信箱
本身有权威，对别的没有" —— **唯独没保护"已读"**。而"已读"恰恰是唯一一个"用户先改、
服务器后知道"的字段，最需要这条保护。

两个触发方式：推送还在路上，同步先回来了；或者推送**失败了但被静默吞掉** —— 桌面端和
安卓端各有两层 `catch` 把失败吃掉，界面永远显示成功。

**改了三处**：

1. 同步结果合并时，"已读"只能从"未读"变成"已读"，不能反过来 —— 除非服务器明确说它已读。
   代价写进了注释：在网页版邮箱里把邮件**标回未读**，同步不过来。这是有意的取舍。
2. 加了一个"已经在本地标了、还没确认推到服务器"的队列。队列里的条目，同步结果一律
   不许改动它，**两个方向都不许**；下次同步前会自动重试一次。
3. 推送失败不再假装成功 —— 两个平台的接口都改成如实返回成功/失败和原因。

### 安卓通知栏那个"标记已读"，以前 100% 会回退

从通知栏点"标记已读"，以前**只写本地缓存、从不告诉服务器**。代码注释给的理由是"这个
进程里没有网页界面可以调"，但这个理由不成立 —— 同一个进程拿得到凭据，推服务器的函数
也是现成的。所以下次同步必定回退成未读，必现。

现在通知栏标记会落一条待推送记录，交给一个带指数退避、最多重试 5 次的后台任务推上去；
同步开始**之前**先把队列推完（放后面等于白推）。推不上去的时候，界面上的已读状态和
未读角标也会保持一致，不会出现"行是已读、角标还亮着"。

### 加了一条门禁，而且证明了它真的会拦

新增 `check:seen`，**驱动真实的合并逻辑跑 9 条断言**，不是用正则去扫源码 —— 正则只能
抓改名，抓不到有人把逻辑改回"整条覆盖"。

把修复故意改坏之后：**2 条断言立刻报错，退出码 1**；恢复后 9 条全过。

## 一键已读

收件箱和验证码两个界面各加了一个按钮，**不用先进编辑模式**。

- **收件箱**：标题栏上一个打勾圆圈按钮，**只在真有未读时才出现**，按一下所有账号的
  未读全部标为已读。按账号分组批量提交 —— 300 封未读是 2 次请求，不是 300 次。
- **验证码**：作用范围**在提示里写死了** —— 只影响验证码列表里的记录，收件箱里那封
  邮件本身不受影响。不让人以为按一下全清了但其实没有。

## 设置里弹出的框，左右不再留白

**根因是一条 CSS 规则的选择器漏了最常见的那一种。** 把弹层拉成全屏的规则只写了
"宽弹层"和"全屏弹层"两种，而设置里那些确认框两种都不是，于是落到了另一条规则上，
左右各留 20px。

**平板更严重**：宽度 840px 以上不匹配那条手机规则，退回"固定 560px 居中" ——
1024px 的平板上**左右各留 232px**，而同一个设置页里的分区弹层却是全屏的。同一个操作流
里两种形态。

现在改成**底部抽屉**：左右铺满、贴着底、高度由内容决定、只有上面两个角是圆的，
并且避开手势条和键盘。用真实浏览器量出来的结果：

| 屏幕 | 左边距 | 右边距 |
|---|---|---|
| 360×800 手机 | 20px → **0** | 20px → **0** |
| 820×1180 平板 | 20px → **0** | 20px → **0** |
| 1024×768 安卓平板 | **232px → 0** | **232px → 0** |
| 1440×900 电脑（对照） | 440px 不变 | 440px 不变 |

电脑端一点没动。

## 主页三个数字，点进去就是筛好的

那三个数字（今天要发 / 今天已发 / 今天失败）**本来就能点**，问题是点进去只是打开列表，
**没带筛选条件**，还得自己再筛一次。

现在点"今天失败 3 次"，直接就是今天那 3 条失败记录。列表上方多一个药丸形的小标签，
写的就是你刚才点的那句话，**点一下就取消筛选**回到完整列表 —— 不会出现"被筛了却看不
出被筛了"。

**"今天"这个限定是真做了的**：筛选用的谓词和主页算那个数字用的是**同一条**，所以主页
说 8，进去也是 8，下面就 8 行，能当场对上。

（"今天已发"没有直接用现成的"发送"筛选 —— 那个筛选把**失败的发送也算成发送**。）

## 提醒不再一直占着屏幕

全应用盘过一遍，共 9 套提示机制，其中 4 套是常驻不消失的。改的是用得最多的那一套
（61 处调用）：

| 类型 | 自动消失 | 能手动关 | 为什么 |
|---|---|---|---|
| 提示 / 成功 | **7 秒** | 是 | 讲的是**已经发生过的事**，字消失了事实也不会变 |
| 警告 / 危险 | 不消失 | **是** | 讲的是**现在仍然成立的状态**，自己消失会让人以为问题解决了 |

7 秒的依据：提示条比右下角那种小浮层装得多（一个标题加一句话，常常还带路径或服务器
原话），4.2 秒读不完；但它是嵌在页面里的，不像浮层那样碍事，也不需要 9 秒。

顺手修了一个真回归：有几个对话框是以提示条开头的，加了关闭按钮之后，打开对话框时
焦点会自动落到"关掉这条消息"上 —— 已排除。

还有一处硬编码的英文 `Dismiss`（中文界面下读屏软件会念英文），改成走翻译。

## 同步：换个 WiFi 不再永久失联

配对时记下的对方地址，**此后再也不更新**。所以路由器换个租约、手机重连 WiFi、
笔记本睡眠恢复之后，配对就**永久失效，而且不告诉你** —— 只能重新扫码配对。这是
"同步莫名其妙就不работа了"最常见的原因。

现在双方在**已加密的信封内部**告诉对方"我现在在哪儿听"，地址变了自动跟上。配对也
第一次变成**双向**的 —— 以前只有扫码那一方能主动发起同步。

安全上收紧了两处：对方通告的地址要过一道校验才可能入库（防止一台被攻陷的已配对设备
把同步流量引到局域网外），**本机通告出去的地址也要过同一道闸**（本机可能有 VPN 或
容器网卡的公网地址，照原样通告等于把它告诉对端）。

另外加了**"立即同步"按钮**，不用干等 90 秒。失败时**如实说明是哪一种失败**：
对方从没告诉过我们地址 / 那个地址没有回应（同时列出三种可能，因为从这一侧确实分辨
不出是哪种）/ 对方拒绝了（带上它的原话）/ 出错了（带上原文）。**没有笼统的"同步失败"。**

## 没有做的，和没有验证的

**云中转没有做。** 需求是"像微信一样同步"。调研结论：中转能解决"不在同一个 WiFi"，
但**解决不了"手机上 App 没开着"** —— 安卓上这个应用没有后台常驻服务。要真的像微信，
还必须加推送（Google FCM），那意味着引入 Firebase 依赖、推送 token 注册到服务器、
通知权限、以及重新申报应用商店的数据安全条款 —— 这是整件事里最大、也是隐私影响最大的
一块，方向上和"防追踪、别收集我信息"是相反的。工作量：服务端 1-2 天，客户端改造好几天
且风险高（要动防重放的账本），推送是另一个独立工程；还有永久性的运维成本，而这个应用
现在这块是零。留给下一轮决定。

**全局界面统一这一轮没做。** 用户在"全局统一 / 视觉升级 / 只修点名的问题"里选了
第三个。这一版只动了点名的那几处。

**没有真机验证的部分**（编译通过和门禁通过都不等于功能有效）：

- 安卓端内嵌图片是不是真的显示出来了；
- 安卓通知栏标记已读是不是真的不回退了；
- "立即同步"按钮按下去界面实际长什么样。

这三条都需要装到手机上才算数。桌面端的图片缓存往返、已读合并逻辑、地址自愈逻辑都有
自动化断言覆盖，可以当数。
